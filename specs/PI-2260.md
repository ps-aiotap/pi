## Root cause (hypothesis + evidence)

**PI-specific hypothesis:** PAR (beta) shows **open quantity** and **closing quantity** as identical and does not reflect period adds/reductions. That pattern is consistent with upstream `position_data` not populating `period_quantity_added` / `period_quantity_sold` (and related period fields) for the selected range, **or** the Report Book / widget binding displaying **opening_holding** / **closing_holding** incorrectly for PAR beta (e.g. wrong period bucket or stale API payload).

**Evidence in repo (Lambda shaping):** `PerformanceApiReport` maps holding and quantity fields from `position_data` into nested period objects — e.g. custom period uses `opening_holding`, `closing_holding`, `period_quantity_added`, `period_quantity_sold`:

```652:654:av_v3_lambda/src/PerformanceApiReport/par_response.py
            "opening_holding": safe_float(position_data.get("custom_opening_holding", 0)),
            "period_quantity_added": safe_float(position_data.get("period_quantity_added", 0)),
            "period_quantity_sold": safe_float(position_data.get("period_quantity_sold", 0)),
```

MTD (and other buckets) use analogous `mtd_*` keys (`710:711:av_v3_lambda/src/PerformanceApiReport/par_response.py`). If the API returns zeros for adds/sold while open/close holdings match, the UI will mirror that.

**Also check:** `av_v3_lambda/src/AUMReport/par_response.py` and `av_v3_lambda/src/PAR-Summation-Calculations/par_response.py` if PAR beta routes through a different Lambda. Dashboard side: `dashboard/src/app/asset-vantage/report-book/report-book.component.ts` (how PAR beta invokes the API and which columns bind to quantity).

**Examples (not exhaustive):**
- PAR quantity / open-close: `av_v3_lambda/src/PerformanceApiReport/par_response.py` (period quantity rollups throughout `get_response`)
- Report Book UI: `dashboard/src/app/asset-vantage/report-book/report-book.component.ts`
